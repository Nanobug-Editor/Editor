## 1. 目标与依据

目标是让插件作者通过公开 SDK 完成资源清理、定位慢请求，并验证包是否适用于目标宿主。保留当前 WASM、能力协商、实例归属和事务更新机制，不增加 crate、第二份文档状态或插件专属宿主接口。

依据：[平台规格](plugin-api-platform.md)、[社区基础规格](plugin-api-community-foundation.md)、[社区 07 工单](../tickets/plugin-api-community-foundation/07-activation-and-compatibility.md)及其[验收](../verification/plugin-api-community-foundation/07-activation-and-compatibility.md)、[隔离开发方案](plugin-development-packaging.md)及其[验收](../verification/plugin-development-packaging.md)、[日志验收](../verification/plugin-runtime-logs-verification.md)。外部系统的借鉴及来源集中在[前置调研](plugin-system-improvements-research-2026-10-21.md)，本方案不重复比较正文。

代码核验基线：当前工作区 HEAD `fc9dc531ef991315d73e21c8a092f12a0f1ff78b`。工作区已有 UI 提取、协议、管理器等大量未提交修改；本方案引用当前文件，不宣称这些修改均已发布或通过联合验收。实施前重新固定输入，保留既有修改，不从历史记录推导当前测试通过。

### 1.2 首期范围

交付三个可组合模块：SDK 生命周期助手、宿主运行诊断、兼容验证。首期验证工具包括静态包检查、隔离开发会话报告及维护者固定矩阵；不建设通用测试脚本语言。

不包含 WASM 源码断点、自动故障二分、远程遥测、OS 级原生程序沙箱、新授权流程、多语言 SDK、WIT/JSON 传输重写或整个能力元数据框架。业务插件源码仍在独立仓库，测试输入不进入发行或 SDK。

## 2. SDK 生命周期助手

### 2.1 不能统一抹平的资源语义

| 对象 | 当前实际释放语义 | 助手处理 |
| --- | --- | --- |
| HTTP 流 | `Finished/Failed` 后仍需 `CloseResource`；取消与关闭不同 | 终态只报告一次；关闭流与轮询定时器，单独报告清理错误 |
| 单次定时器 | 触发回调前已释放，不能继续 reset | 收到匹配回执后移出本地拥有集合，不再次关闭 |
| 周期定时器、订阅、观察 | 显式关闭，或由实例退役回收 | 在功能结束时关闭；某些订阅失败要求重新枚举，不能盲目重订阅 |
| 编辑器请求 | [终态通知代码](../../../crates/plugin-runtime/src/instance/editor_requests.rs)在通知前移除请求与句柄 | 收到终态后仅结束本地意图；未终结时取消/关闭，不对终态再发无效关闭 |
| 进程及已发生外部副作用 | 关闭可能终止进程；取消不回滚副作用 | 首期不纳入默认通用清理策略，继续使用显式进程与事务接口 |

SDK 不更改宿主生命周期协议。若实施发现某种资源语义不明确，先补该公开类型附近的说明与行为回归，不以助手掩盖宿主缺陷。

### 2.2 三个小接口承担实际复杂度

在 `plugin-protocol/src/api/guest/` 下新增 `resources.rs`、`intent.rs`，在 `plugin-protocol/src/http/` 下新增 `task.rs`；通过现有 guest/http 模块公开，不搬迁无关协议源码。

| SDK 类型 | 调用方使用方式 | 隐藏的实现 |
| --- | --- | --- |
| `ResourceGroup` | 接管有明确清理类型的定时器/订阅；处理释放回执；显式 `close_all` | 去重、拥有关系、反向清理、已回收处理与失败收集 |
| `EditorIntent` | `replace` 发起替代意图；`update` 接收对应通知；`cancel`/`close` 结束 | 原意图失效、关联过滤、取消结果、终态自动回收差异 |
| `HttpTask` | `start`；将匹配通知传给 `on_event`；`cancel`/`close` | 流与轮询定时器的事务式初始化、有界拉取、终态与部分失败清理 |

三者不重复拥有同一句柄：`HttpTask` 自己拥有流和轮询定时器，`EditorIntent` 自己拥有请求，不能再把这些内部句柄登记到 `ResourceGroup`。资源组首期负责独立订阅和定时器，不做任意对象容器。接管使用带清理语义的类型化入口，避免调用方给任意句柄猜一个清理枚举。

新拥有类型不提供 `Clone` 或序列化，标记 `must_use`；原始 `ResourceHandle` 及低层函数保持兼容。SDK 的拥有关系防止普通误用，不代替宿主的跨实例、权限和作用域校验。

### 2.3 关闭与失败规则

1. 所有 `close` 操作在助手本地幂等；先停止接收旧意图结果，再进行清理。资源组按接管逆序清理，某项失败仍继续清理其他项。
2. `CleanupReport` 分别列出已关闭、已由宿主回收、仍需清理及安全错误码。只能对该助手确实拥有过的句柄处理 `InvalidHandle`；权限错误、未知状态和无法确认的关闭失败不能吞掉。
3. 失败条目保留供显式再次清理，已成功条目删除；助手不得无界累积失败句柄或自动无限重试。无法清理旧意图时拒绝继续分配替代资源，并给出结果。
4. `Drop` 不调用宿主、不 panic、不尝试异步等待。显式关闭是正常路径；trap、预算耗尽和插件退出仍由 `Instance::quiesce` 兜底。源码示例必须展示功能退出的关闭路径。
5. 面板暂时隐藏不自动等同于功能结束。插件按已有可见性事件决定暂停轮询还是关闭功能，后台任务继续遵守已声明用途，SDK 不新增隐藏即停用规则。
6. `EditorIntent::replace` 先验证本地参数，使旧意图失效并清理，再启动新请求；新请求失败返回失败，不假装旧请求恢复。写操作的取消方式显式传入，绝不自动重试编辑或承诺回滚。
7. 意图过滤不能只依赖 SDK 计数：仍核对宿主句柄、实例、文档及 revision。计数溢出拒绝继续使用；跨热更新不恢复旧句柄。

资源组建议默认最多登记 256 项，各类型仍遵守宿主更小的实际限额；接管失败必须把尚未接管的资源返回调用方，不得丢弃唯一句柄。失败记录与活动条目共用上限。对于宿主已经分配成功但助手无法接管的路径，创建助手负责显式关闭并返回清理结果。

### 2.4 HTTP 调度与限额

`HttpTask::start` 先检查已协商的 HTTP/定时器能力及本地参数，然后申请流、申请轮询定时器。第二步失败时立刻清理第一步；主错误和清理错误分别返回。检查协商不是预先授权，实际调用继续由宿主检查权限。

`on_event` 只响应本任务定时器，并对一次回调最多拉取 8 个事件或 256 KiB，达到任一上限就返回；这是建议默认值，不能超过现有宿主预算。无数据立即返回，下一次回调继续，不在访客回调里阻塞等待或忙循环。

返回原始有序 Header/Chunk/终态事件；不默认拼接整个响应，不隐式解码跨 Chunk 的 UTF-8，不把非 2xx 当传输失败。业务协议、鉴权头和文本解析留在插件。取消保留“远端副作用可能已发生”的原语义；成功接收与清理失败允许分别呈现。

### 2.5 兼容与证明

助手只组合现有协议 7 调用，原则上不新增能力版本或权限。SDK 内容摘要会变化，新文件必须加入 `sdk_export.rs` 的 `SDK_FILES`；接口说明放源码注释，可编译示例不依赖仓库路径，Markdown 不进入导出。

旧 `EditorTask` 和原始函数保持行为不变；不强制既有插件迁移。新调用方使用新助手，若仅新增 Rust 源码接口便能实现，不提升宿主能力版本。只有新增可观察 wire 行为才按原规格独立评审能力版本。

用两个独立 SDK 构建消费者证明：一个云查询消费者验证 HTTP/定时器，一个文档观察消费者验证订阅/替换意图。新增测试候选放在 `tests/fixtures/` 对应新目录，保留原固定 ZIP 与摘要；不覆盖历史包以伪造兼容。实际业务插件迁移属于后续明确范围，不能顺带修改独立 Git、Rust 等仓库。

## 3. 运行诊断

### 3.1 模块位置与身份

建议新增 `plugin-runtime/src/observability.rs` 及其同目录子模块，封装计时、聚合、有界记录与导出数据模型。由现有 `HostResources` 持有共享实例，与 `RuntimeLogs` 并列；不把统计写成普通日志，也不复制请求状态机。

诊断身份包括：宿主会话、插件 ID/包摘要、逻辑作用域、实例 incarnation、宿主生成的操作编号及可选父编号。请求编号不全局唯一，不能只用 guest request ID 关联；跨插件调用分别保留调用者与执行者。

准备期间尚无活跃实例的工作使用候选操作身份，提交时关联新实例，失败后不能归入旧实例。应用级实例由共享运行时拥有者计一次，不能每个工作区重复相加。诊断身份不包含权限，也不能用于执行宿主操作。

### 3.2 观测位置与时间含义

| 阶段 | 现有接入点 | 首期观测 |
| --- | --- | --- |
| 排队 | `extensions/worker.rs` 的投递与 `worker/runner.rs` 的取出；需求 `demands.rs` | 入队到开始处理；取消、拒绝、合并和丢弃分别计数 |
| 激活 | `manager/activation/driver.rs`、`preparation.rs`、`lease.rs` | 触发原因、共享一次准备的等待数、准备/提交结果 |
| 访客执行 | `Instance::call`、`call_inner`、`instance/capability_calls.rs` | 回调总墙钟耗时、可取得的 fuel 消耗、同步宿主调用耗时和错误类别 |
| 异步完成 | `Completion`、`EditorRequest::begin/finish/cancel` | 受理、开始、终结；超时与迟到结果拒绝次数 |
| HTTP/原生等待 | `http.rs`、现有进程/准备注册与回执 | 已发起到结果/取消确认的等待；真实退出与仅撤销授权分开 |
| UI 发布 | `Instance::call_capability` 的结果校验及 worker 发布 | 成功/拒绝次数、已有编码数据的字节量、发布次数和过期丢弃 |

只在实际能关联的接缝记录阶段；未覆盖部分标记 `unobserved`。嵌套时间允许重叠，不能简单相加；“访客回调耗时”包含同步宿主调用，未能可靠扣除时不得标为纯 WASM CPU。fuel 也不是 CPU 时间。

首期不承诺原生进程 CPU/RSS 或逐帧渲染归因；它们需要另行平台采样。UI 统计仅表示校验/发布，不能叫作绘制耗时。为统计字节量不得额外序列化整棵 UI。

### 3.3 资源统计与回收证据

分类快照从 `ResourceRoots` 和对应实际集合读取，包括请求、HTTP、定时器、订阅、树、虚拟文档及进程引用；它是读取投影，不是第二个可变资源注册表。诊断拿取不可变值，不长期持有资源 `Arc` 或延长生命周期。

数量相近不等于同一资源。回收检查按已记录 incarnation 对比，区分活跃拥有资源、已撤销但等待 OS 收尾、确认已结束和未知结果。HTTP 的同步 OS DNS 即使已经取消，也可能占用原 worker 等待返回；不得强行宣称线程已退出。受管缓存文件与逻辑快照不计作运行资源泄漏。

停用期间允许有界的收尾等待；到期输出剩余种类及状态，而不是删除统计伪造零值。重启或回滚恢复的是新 incarnation，其资源不能被算成旧实例泄漏。

### 3.4 容量、隐私与界面

- 默认只维护轻量累计计数和概况；详细捕获由用户开始，默认 60 秒后结束。建议全局最多 4096 条记录、4 MiB；单插件最多 512 条。容量耗尽明确记录截断计数，不能拖慢或改变业务结果。
- 完整轨迹存在丢失时标记 `partial`，不得据此判定资源已全部释放。当前资源快照按需从拥有者读取，不能由采样轨迹推算。
- 仅保存白名单元数据：阶段、相对时间、版本、错误码、数量及有界声明标识。禁止保存文档正文、HTTP URL/query/header/body、Token、进程 argv、环境变量、用户路径和任意日志正文。作用域导出为会话内不透明标识。
- 默认不落盘；用户显式导出到选定位置。导出带 `schema_version`、宿主/SDK/包身份、捕获范围、覆盖率、丢失数和平台。不能悄悄把现有文本日志并入“脱敏”报告。
- 在当前[插件详情模块](../../../crates/editor-app/src/extensions/management.rs)增加“运行诊断”页面：概况、最近慢操作、资源数、开始/停止捕获和导出。未激活显示休眠及未采集，不把无数据画成零耗时；已有日志页保持用途。
- GPUI 页面只读不可变快照，打开时最多每秒刷新一次，关闭后停止界面刷新。复用 `editor-ui` 现有表格/列表/按钮入口与 i18n；本批不重写通用控件或管理器布局。

诊断故障不能改变请求完成、取消、安装或退出行为。插桩不能绕过现有即时信任撤销路径，也不能在持有完成门锁时回调用户代码。性能比较先在相同输入下测量关闭与开启捕获的差值，容量和刷新上限必须有确定性测试。

## 4. 兼容验证工具

### 4.1 静态检查入口

CLI：`editor-app --plugin-check <plugin.zip> --format json|text`。只接受已生成的包，不隐式构建项目、下载依赖、打开工作区、授予权限或实例化 WASM。目标是运行该命令的宿主；检查多个宿主时分别运行其确切可执行文件。

复用 `Package::read` 与现有声明/能力校验。建议在 `plugin-runtime` 新增 `validation.rs` 承担报告模型，校验逻辑仍在原拥有模块；`package.rs`、`capabilities.rs` 在拒绝点产生可 downcast 的结构化原因，原 `anyhow::Result` 调用方继续可用。不能根据人类错误字符串推断稳定诊断码，也不建立第二个 ZIP 校验器。

现有 `Requirements::negotiate` 返回字符串错误，结构化改造应在同一协商实现内产生类型化原因；保留原方法签名作为兼容入口，新的宿主校验使用类型化结果。不得为报告在 CLI 再复制一套版本匹配规则。该 Rust 层增量不改变 guest wire 错误枚举或已有协商结果。

首批结构化类别覆盖包/路径/资源限额、清单格式、宿主/协议范围、必需能力缺失、最低 minor 不足、声明所需权限缺失。可选能力不可用作为明确降级项；运行时是否实际授权不属于静态通过结论。暂未结构化的错误使用 `unclassified` 并使检查失败，不假造字段位置。

报告至少含 `schema_version`、工具身份、ZIP SHA-256、内部包摘要、可安全解析的 ID/版本、协议、协商结果、检查覆盖范围，以及 `diagnostics[]`。每条诊断含稳定码、severity、阶段、包内文件、可用时的 JSON Pointer/行列、所需与可用版本、安全说明。损坏包不能强制要求有 manifest 身份。

工具身份以可执行文件摘要、SDK 摘要和构建版本为准，不仅使用当前可能相同的 `0.1.0` 版本号。文件无法读取时摘要为空并给出原因；结构化报告不嵌入任意原始错误链或清单字段值，说明由代码和受限字段生成。首期可以在首个无法安全继续的校验处停止，报告 `stopped_at`，不承诺一次枚举全部包错误。

静态检查不会执行或分析全部业务路径，因此不能证明每个动态调用都声明了正确最低版本。清单/声明式 UI 可验证的下限直接检查，其余需要真实消费者回归；报告显式区分两者。

保持 `inspect_package` 当前成功 stdout 为 manifest JSON，市场调用方无需同时升级。内部共享结构化原因；市场接入新报告格式属于后续独立变更，本方案不修改市场流程。

### 4.2 隔离开发报告

在既有 `--plugin-dev` 增加可选 `--report <path>`，沿用原项目、工作区、profile、授权和 `reload`/`stop` 流程。它仍是交互式隔离开发，首期不提供自动执行任意插件业务的脚本语言，也不将观察报告称作全面兼容认证。

报告记录本次成功加载的包/SDK/宿主身份、激活原因、开发者实际触发的操作摘要、重载结果及停止清理。没有触发过的能力标记 `not_exercised`。声明式包无 WASM 时，不把“没有激活访客”判成错误。

重载每次使用独立候选身份；失败保留旧实例时，同时记载候选失败和旧实例继续可用，不能用一次失败抹掉整个会话状态。报告开启/关闭不修改默认授权、工具路径或依赖安装流程。

结果采用 `passed / failed / inconclusive / not_exercised` 并保留阶段覆盖。调用业务已失败、包准入失败或已确认清理残留时为 `failed`；宿主崩溃、超时、用户强制结束或观察缺失而无法判定时为 `inconclusive`，附单独终止原因。有任一必需检查未执行，不能聚合成 `passed`。

首期报告的必需检查固定为包准入、隔离宿主启动、实际激活（仅可执行插件）和停止回收；启动后一直未使用的可执行插件，其激活项为 `not_exercised`，整体为 `inconclusive`。可选的业务观察不影响已完成的生命周期检查，但必须在覆盖表中列为未测；生命周期 `passed` 的名称和展示不能省略“生命周期”限定。

新工具模式约定退出码：0=请求检查完整通过；1=被测包或已执行检查失败；2=参数/输入错误或无法完成评估；3=用户取消。现有未启用报告的开发命令保留当前退出行为。输出 JSON 时 stdout 只含结构化结果，诊断提示走 stderr。

会话报告由父开发控制器在正常停止或异常退出时写入；过程中只保留有界的脱敏检查点，正常结束原子替换指定报告。报告文件与临时输出限定于用户选定位置，不写插件项目的其他文件。整个父进程被强制终止时只能保留最近检查点，并明确不完整，不能保证最终报告必定生成。

### 4.3 固定兼容矩阵

兼容矩阵是维护者持续回归，在现有 Rust 集成测试和原生测试内组织，不新增插件测试专用宿主能力。主入口复用 `compatibility.rs`、`activation.rs`、`cloud.rs`、`editor_requests.rs`、`hot_update.rs`、`scoped_instances.rs` 及对应应用集成。

| 输入/检查 | 证明内容 | 不证明内容 |
| --- | --- | --- |
| 固定旧 ZIP 原字节 + 新宿主 | 稳定接口的既有消息与语义仍可用 | 新 SDK 源码兼容 |
| 同一消费者源码 + 新导出 SDK 独立构建 | 新 SDK 可开发、可打包、使用助手可运行 | 旧 ZIP 仍兼容 |
| required/optional/最低版本的正负样本 | 拒绝/降级和能力下限符合声明 | 所有插件业务都覆盖 |
| 激活、取消、禁用、重载失败与恢复 | 已声明生命周期及数据保护 | 外部副作用回滚 |
| SDK 助手两个独立消费者 + GPUI 原生交互 | 真实调用、迟到结果与视图退出行为 | macOS/Linux 未执行场景 |

账本沿用 `tests/fixtures/packages/inputs.json` 的身份记录方式，按条目记录 archive/hash、源码来源、SDK 摘要、工具链与适用场景；旧包绝不重建覆盖。新候选另建条目，缺失输入或 hash 不符立即失败，不自动改用同名新包。

不同宿主源码快照使用独立 Cargo 输出目录，先运行 `cargo metadata --no-deps --format-version 1` 核对来源。相同版本号但 EXE/SDK 摘要不同必须分开报告。矩阵首期以候选宿主和实际保留的受支持基线为输入；不虚构尚无产物的历史版本，也不隐含无限期维护所有宿主。

不存在新入口的历史宿主仍可运行其已有测试/观察路径；无法自动获取的项目标记未覆盖，不能假定旧宿主支持新 CLI。发行支持范围由实际可复现矩阵明示。

## 6. 实施顺序与完成标准

以下是建议阶段，不是已发布工单。阶段依赖为 S1 → S2、S3；S3 → S4；S2/S4 → S5。表格不授权启动并行代理。

| 阶段 | 可交付结果 | 完成标准 |
| --- | --- | --- |
| S1 固定行为与输入 | 资源释放语义表、旧包矩阵输入、报告 schema 草案和覆盖清单 | HTTP/请求/单次定时器差异由现有真实输入复核；固定摘要，缺失项明确，不先重建旧包 |
| S2 SDK 生命周期助手 | 三个助手、源码说明、两个独立 SDK 消费者 | 初始化失败、替换、终态、重复关闭、trap/退役兜底全部有可观察结果；导出 SDK 独立编译运行 |
| S3 运行诊断核心 | 有界观测与真实资源快照 | 关联身份正确，取消/回滚不混归，脱敏/容量/并发测试通过，不改变原操作结果 |
| S4 原生诊断与开发报告 | 详情页、捕获导出、`--plugin-dev --report` | Windows 深浅主题、中英文、键盘/滚动、停止/异常退出报告正确；报告能区分未测与失败 |
| S5 静态检查与持续矩阵 | `--plugin-check`、结构化错误、固定输入矩阵 | 市场旧校验输出兼容；正负准入和原字节/重建两类证据分开；各阶段规定门禁及必要原生行为均完成 |

S3 可先用已有 SDK 消费者取样，不要求批量迁移所有插件。S5 的校验结构化应按拒绝点逐步落地，以实际覆盖为准，不为一次报告引入全量能力代码生成器。

纯状态测试可利用模块私有的执行接缝返回可观察操作与结果；实际完成标准仍包含通过公开 Package/Manager 的真实 WASM。不得只测试调用次数、只验证新 SDK 编译，或用测试专属宿主接口绕开授权/退役。

代码实施各阶段执行 `cargo fmt --check`、`cargo test --workspace --exclude editor-app`、`cargo check --workspace`。追加受影响协议/运行时测试及 `cargo test -p editor-app <实际过滤词>`；相关真实包测试按 ignore 原因直接构建夹具后显式执行 `--ignored`，不调用旧脚本。原生 UI 用真实 Windows 会话检查相关输入、显示、滚动与缩放。

性能使用相同宿主 profile、相同输入与独立输出目录比较捕获关闭/开启；记录平台、样本数、调用量和原始结果。先测测量噪声，再设有依据的回归门槛；本方案不凭空承诺“零开销”或一个尚未测过的百分比。资源/记录限额和业务结果等价必须确定性通过。

## 8. 风险与范围收口

- **助手清理反而改变行为：** 用原宿主语义表区分自动回收与显式释放，保留低层接口；不自动终止进程或回滚事务。
- **观测延长资源寿命或制造死锁：** 仅复制标量与不透明身份，不持有资源引用、不在业务锁中做 IO；诊断输出独立于完成门。
- **伪精确性能指标：** 明示嵌套、未观测及截断，时间按单调时钟统计；原生 CPU/RSS 与渲染归因延后。
- **静态验证被误当执行安全：** 报告覆盖声明/包结构，保持原生程序无 OS 沙箱保障的说明；不执行第三方代码来完成市场准入。
- **只验证新编译包：** 固定旧 ZIP 以摘要准入，与新 SDK 候选分开命名和存放；缺失不得重建替代。
- **工作区持续变化：** 每阶段固定源码、宿主、SDK、包和工具链身份；只将本阶段实际验证的输入写入交付记录。

首期证明对象为两个独立测试消费者和既有固定包。后续依据作者实际使用反馈决定是否增加公开自动业务场景执行器、更多资源助手或更深的性能采样；这些不纳入本方案的完成条件。
