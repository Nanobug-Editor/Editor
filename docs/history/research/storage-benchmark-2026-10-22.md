# 文件历史存储：Windows 本机微基准

状态：调研实验，非产品验收；没有实现 `editor-history` 或修改产品保存流程。后续已确认的产品范围见[基础方案](../specs/local-history.md)。

日期：2026-10-22。机制和一手依据见[存储方法调研](storage-methods-sources-2026-10-22.md)。程序：[benchmark_storage.py](benchmark_storage.py)；原始环境、逐项样本和输入源码哈希：[JSON](storage-benchmark-2026-10-22.json)。

后续补充：[快照与文件变更日志＋旧内容引用的比较](history-models-benchmark-2026-10-22.md)，包含 LZ4、文件结构轨迹和较长历史的索引测试。本文的相邻字典链不是 IDEA 的旧内容引用模型；两轮捕获语义不同，延迟数字不能直接拼成一个排名。

## 测量范围和环境

- Windows 11，AMD Ryzen 9 9950X3D，32 个逻辑处理器；Python 3.12.14、SQLite 3.53.1、Zstd 1.5.7。Zstd 通过 `ctypes` 调用本机既有 Git 运行时的原生 DLL；没有安装依赖。处理器名称来自 `Get-CimInstance Win32_Processor`，其余原始版本见 JSON。
- 本仓库 `editor-core`、`editor-ui`、`editor-app` 的 Rust 源码片段衍生输入；起始文件大小三档约 8、64、512 KiB，各 4 个文件，每文件 48 个版本，共 576 个版本，逻辑内容总计 **117.43 MiB**。前插和长行替换会改变后续版本大小，档位是起始体积，不是固定大小承诺。
- 四种确定性合成轨迹：稀疏单行替换、分散多行替换、开头插入、偶发大范围重写；包含重复保存和回退重现。随机种子 `20261022`。这是源码衍生的合成编辑轨迹，并非真实用户编辑遥测，也未覆盖所有语言、二进制或极大文件。
- 每种方案 3 个全新数据库，轮内打乱方案顺序，共 **18 组**。每组 576 次版本提交；每个方案的汇总 p95 来自 1728 个样本合并排序的 nearest-rank，不是三次 p95 的平均值。体积、CPU 和 GC 总耗时取三组中位数。
- 每组都用 SQLite BLOB，`page_size=4096`、WAL、`synchronous=FULL`、8 MiB 页缓存、`mmap_size=0`、1000 页自动 checkpoint，每版本单独事务提交。同一 `(file, sequence)` 索引、SHA-256、相同历史条目序列；仅基线 raw 不做内容去重，额外的 rawcas 隔离去重与压缩的收益。
- 每组数据完整提交、手动 `wal_checkpoint(TRUNCATE)`、关闭并重新打开、逐版本校验后测随机读取。读延迟是**热 OS 缓存下读取并重建版本完整内容**，没有跨请求解码内容缓存；一个请求内部可以复用已解码基线。不是冷盘延迟，不包含 GPUI、语法高亮、diff 算法或窗口绘制。
- 体积为 checkpoint 后 `.sqlite` 的文件长度，包含对象、索引和页内空闲，WAL 已截断；没有测运行中 WAL 峰值、NTFS allocated size 或设备写入量。

## 六组实际编码

| 代号 | 实现 | 依赖与去重 |
| --- | --- | --- |
| raw | 每版本未压缩完整内容 | 不去重、无基线依赖 |
| rawcas | 未压缩完整内容＋SHA-256 对象复用 | 同内容只存一次、无基线依赖 |
| zstd1 | Zstd level 1 独立完整内容＋对象复用 | 无共享字典、无基线依赖 |
| zstd3 | Zstd level 3 独立完整内容＋对象复用 | 无共享字典、无基线依赖 |
| chain16 | Zstd level 1，用前一版本原始内容作字典 | 每 16 个版本完整检查点；深度到 15 时也转完整对象；重复内容复用原对象及其依赖 |
| anchor16 | Zstd level 1，新内容引用完整检查点作字典 | 最多一层参考差分；重复内容可沿用此前对象的原检查点，不能称所有条目都绑定当前组 |

这里的参考差分是真实 Zstd 字典编码，未实现或测量 Fossil、VCDIFF 或文本 diff 补丁。使用 `ZSTD_compress_usingDict` / `ZSTD_decompress_usingDict`，每次加载字典的成本计入；没有预编译字典缓存。具体接口语义见 [Zstd 1.5.7 公开头文件](https://github.com/facebook/zstd/blob/v1.5.7/lib/zstd.h#L890)。

所有组采用相同 SQLite 容器，不能将 raw 的成绩说成 VS Code 的实测；也不能根据这一轮判断 BLOB 与独立对象文件谁更快。IDEA 的 ChangeSet 捕获语义没有在这里重建。

## 测量结果

单位：体积 MiB，延迟 ms；p95 越低越好。

| 方案 | 数据库体积 | 记录 p95 | 随机打开版本 p95 | 列出该文件历史 p95 | 清理并压实体积的总耗时中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| raw | 117.85 | 7.006 | 0.765 | 0.0265 | 598.23 |
| rawcas | 90.69 | 1.853 | 0.783 | 0.0271 | 421.63 |
| zstd1 | **26.37** | **2.171** | **0.623** | 0.0270 | **123.17** |
| zstd3 | 24.87 | 3.033 | 0.688 | 0.0323 | 126.95 |
| chain16 | **20.18** | 2.130 | **4.308** | 0.0411 | 113.54 |
| anchor16 | **20.66** | 2.215 | **1.188** | 0.0324 | 124.79 |

记录样本包含哈希、必要的编码、新对象/版本索引写入、逐次提交及自动 checkpoint；计时从已有不可变内容切片之后开始。**不含**读取编辑缓冲区、生成输入和批次结尾的手动 checkpoint。相同内容命中 CAS 的样本照常计入；这是有重复保存负载下的混合分布。

大文件可能被整体分布掩盖，单列起始 **512 KiB** 档位的 p95：

| 方案 | 记录 p95 | 随机打开版本 p95 |
| --- | ---: | ---: |
| raw | 11.784 | 0.881 |
| rawcas | 10.495 | 1.006 |
| zstd1 | 2.610 | 0.697 |
| zstd3 | 3.900 | 0.841 |
| chain16 | 2.745 | 5.767 |
| anchor16 | 2.709 | 1.548 |

每组完整写入批次的进程 CPU 时间中位数分别为 raw 546.9、rawcas 390.6、zstd1 390.6、zstd3 500.0、chain16 328.1、anchor16 406.2 ms。CPU 计时粒度和混合去重命中会影响这些小样本，不宜按它们声称某个编码器 CPU 吞吐的通用排名；没有测峰值 RSS。

另建 **100 万条元数据**索引，1000 个文件各 1000 条历史；随机取文件最新 50 条，共 3000 次查询：p50 **0.0233 ms**、p95 **0.0347 ms**。这里不读取内容，因此无法据此判断打开版本、diff 或界面布局的速度。六组仅有 48 条/文件的列表数字也不构成独立压缩方案间的明显性能差异证据。

## 正确性、清理和实际限制

- 每组在重新打开数据库后校验全部 576 个版本；清理最早 24 个/文件后，再校验保留的 288 个版本。均以完整内容 SHA-256 对照输入，任何错误会终止运行。18 组共执行 **15552 次**重建校验。
- 清理先删除旧版本索引，再沿内容基线引用标记可达对象，删除不可达对象，提交，checkpoint，`VACUUM`，再 checkpoint。表中 GC 总时间包含这一完整过程，只有保留版本的再次验证排除在 GC 计时之外。
- GC 后数据库体积中位数分别为 raw 60.895、rawcas 45.688、zstd1 14.242、zstd3 13.578、chain16 11.363、anchor16 12.254 MiB。达到版本过期时间并不保证能立即删除该版本对应的全部内容：仍被依赖的基线需要保留或重建。
- 参考实现使用 Python 调度 SQLite/原生 Zstd。读取链需要多次 SQL/FFI 调用，这也是此实现的实际成本；Rust、批量读取、基线缓存或预编译字典可能改变绝对值和比率。相邻版本连续浏览的解码缓存没有测量。
- 数据集小于产品长期保留上限，版本数和文件类型有限；未测并发读写、工具外部改盘、冷启动/冷缓存、实际 UI、diff、异常退出/断电、数据库损坏、边写边清理的尾部延迟、峰值内存、WAL 峰值、设备磨损、独立对象文件、CDC、文本补丁或 OS 快照。因此这些结果不能形成所有方案的绝对排名，也不能称为产品性能验收。

## 对 Nanobug 的条件建议

这是本实验后的工程判断，不是已确认规格：

1. **基础版优先验证 zstd1 独立快照＋全内容去重＋索引**。在这一负载下，较 rawcas 少约 71% 空间，任意历史版本无前序依赖；随机读取和清理实现较直接。将存储与查询封装在 `editor-history` 的小型接口之后，不把编码选择泄漏到 UI 调用方。
2. **空间压力明确后，优先考虑一层参考差分，再考虑链式差分**。anchor16 比 zstd1 少约 22% 空间，随机读取 p95 约 1.9 倍；chain16 只比 anchor16 再少约 2.3%，但读取 p95 约 3.6 倍。可以进一步测“差分没有明显收益就保留独立对象”的自适应选择，但本轮未实现，不能当成已测优胜者。
3. **CDC 不应凭机制直接宣称更优**。大文件、长历史、插入移动、多文件重复可能使它更有价值；需要与这组基线同容器、同持久化、相近优化水平对照后再决定。
4. **列表和内容访问分别优化**。历史列表使用元数据索引并分页；是否采用增量主要影响版本内容重建，不应让列表查询去解压或回放文本。

实验建议本身不替代产品决策。后续已确认的[基础方案](../specs/local-history.md)采用 Zstd 独立全量对象与直接版本索引，明确替代原开发计划的压缩增量与检查点路线；本报告保留原始测量条件及数据。

```powershell
  --dll 'C:\Users\Tmiracle\.cache\codex-runtimes\codex-primary-runtime\dependencies\native\git\mingw64\bin\libzstd.dll' `

```
