# Nanobug 窗口拖动优化历程

日期：2026-10-23。范围：本轮主窗口、子窗口及内部布局拖动排查，重点是完整工作区总窗口的持续快速移动。

当前结果：用户从最初的“明显滞后”，经过“有所改善，但仍不够高刷”，到锁竞争修复后反馈“明显更顺畅”。已确认并修复同步写盘、绘制时重复文件查询和主题复制、后台发布长时间占用 UI 共享锁等问题。**完整工作区稳定达到当前屏幕刷新率仍未验收；清理探针后的普通 Release 已构建，尚未进行同场景拖动复测。**

本文说明每一步为什么做、改了什么、证据能支持什么结论。完整原始路径、进程身份、采样口径和历史失败见[详细验收记录](window-drag-refresh-2026-10-23.md)。

## 最终保留的五项产品优化

| 改动 | 之前的开销 | 现在的行为 | 主要代码 |
| --- | --- | --- | --- |
| 合并窗口尺寸保存 | 每次边界通知都同步序列化会话、写文件、刷盘 | 尺寸不变直接返回；尺寸立即更新内存，停止变化 200 ms 后保存最新状态；正常关闭仍保存 | [app/shell.rs](../../../crates/editor-app/src/app/shell.rs)，`update_window_geometry` |
| 图标规则先筛选再查盘 | 不相关文件和目录也遍历祖先、查询项目标记文件 | 先匹配目录／文件名／扩展名，命中后才查询标记文件 | [ui/icons.rs](../../../crates/editor-app/src/ui/icons.rs)，`matches_icon` |
| 目录分类使用工作区快照 | 每次绘制可见树行都调用 `Path::is_dir` | 根据当前树的扫描快照建立目录索引，绘制时查内存集合 | [explorer/tree.rs](../../../crates/editor-app/src/explorer/tree.rs)，`directory_index` |
| 当次树绘制共用主题 | 每行重复取得、克隆完整主题定义 | 每次资源管理器树渲染取得一次，所有行共用；下次渲染重新取得当前主题 | [editor/view.rs](../../../crates/editor-app/src/editor/view.rs)，`icon_theme` |
| 缩短后台发布临界区 | 持有 UI 也需要的 `Published` 锁时准备插件元数据、诊断等状态 | 先在该锁外准备数据，再短暂持锁统一发布 | [worker/command_epochs.rs](../../../crates/editor-app/src/extensions/worker/command_epochs.rs)、[worker/runner.rs](../../../crates/editor-app/src/extensions/worker/runner.rs) |

这些改动降低了每次输入、绘制和状态读取的成本。产品继续使用 GPUI 的显示器驱动刷新链路，没有加入固定 144 Hz 的刷新循环。

## 第一步：确认刷新来源，移除逐次同步写盘

最初检查了总窗口、原生子窗口、停靠标题、停靠边缘、横向和纵向分隔条。它们共用 GPUI/Base 的原生输入、布局和失效机制，没有发现宿主写死的 60/120/144 FPS 拖动定时器。

这里的目标是**当前显示模式的刷新率**：例如硬件支持 240 Hz，但 Windows 当前设置 144 Hz，程序就跟随 144 Hz，而不是自行切换显示模式。144 Hz 每帧约有 6.94 ms 的时间预算。

第一处明确问题在窗口边界观察器：不论仅移动还是调整大小，每次通知都保存整个会话，包含同步文件操作和 `sync_all`。修复后：

1. 尺寸未改变时直接返回，纯移动不再重复保存尺寸。
2. 尺寸变化立即更新已有内存状态并通知布局，显示不等待落盘。
3. 连续变化只保留一个可取消的保存任务，最后一次变化后等待 200 ms 再保存。
4. 正常关闭沿用现有保存流程，避免刚调整完就关闭时丢失最终尺寸。

**200 ms 是保存合并时间，不是绘制间隔。** 保存本身并未被改写成另一套后台存储机制。

[窗口几何回归](../../../crates/editor-app/src/tests/window_geometry.rs)覆盖连续缩放、相同尺寸不重写文件、立即关闭保存最终尺寸。轻量原生控件夹具的 16 个深浅主题场景测到约 142.14–143.98 次绘制回调/秒，证明共用链路有高刷供帧能力，但不能代表繁忙完整工作区的真实拖动。

## 第二步：核对实际运行的 EXE，纠正验证对象

用户仍然感觉滞后，因此继续核对前台进程，而不是只看构建成功日志。

发现当时确实运行着 **Release**，但生产 EXE 仍是 14:45 的旧产物；此前通过回归的是 `target/release/deps/` 下的测试程序。实际 EXE/PDB、回调反汇编确认旧程序没有新保存逻辑。

随后为同一 checkout 构建独立生产输出，核对产物和实际进程，再请用户真实拖动。外部只读采样结果为：

| 程序 | 连续段时长 | OS 窗口位置变化频率 |
| --- | ---: | ---: |
| 旧 Release | 10.686 秒 | 60.077 次/秒 |
| 包含写盘修复的 Release | 9.193 秒 | 59.608 次/秒 |

这说明写盘问题确实需要修复，但**它没有解决当时约 60 次/秒的主要瓶颈**。这一步是运行产物和验证方法的纠正，没有把重新编译本身算作性能优化。

## 第三步：测量整帧耗时，找到文件树与图标规则

加入临时 GPUI profiler 探针，并用外部约 500 Hz 的只读鼠标／窗口坐标采样同步观察真实拖动。日志写入放在后台，不在 UI 绘制调用中写文件。

完整工作区测得 draw 中位数约 **10.787 ms**，其中 prepaint 约 **7.762 ms**；平台渲染／提交的 CPU 区间中位数只有约 **0.107 ms**。仅绘制准备就已经超过 144 Hz 的 6.94 ms 预算，排查重点转向 UI 的 CPU 工作。

视图类型计时进一步定位到资源管理器 `TreeState`：其 prepaint self 中位数约 **4.255 ms**，占该轮 draw 累计时间约 45%。移动事件会触发 GPUI 全量刷新，所以即使文件树没有变化，这些行也会再次参与布局和绘制。

图标规则当时先查祖先目录中的项目标记，再判断文件名／扩展名是否相关。例如一个只适用于某类配置文件的规则，也会对普通源码行做项目标记查询。

修复将判断顺序调整为：

```text
匹配目录／名称／扩展名 → 不匹配则结束 → 匹配后才查询项目标记
```

保留原有匹配优先级、大小写处理、路径后缀和祖先查询顺序；命中的规则仍实时查盘，没有引入可能过期的跨帧标记缓存。回归直接断言不相关行的磁盘探测次数为零。

随后一段真实拖动测得位置更新 **97.405 次/秒**，draw 中位数约 **6.960 ms**，树 prepaint self 中位数约 **3.23 ms**。用户反馈“有所改善，但是还是不够高刷”。不同轮次的布局、标签和后台负载不完全相同，这些数值展示阶段结果，不能把全部增益归于单一代码改动。

## 第四步：继续降低树行的重复成本

图标规则修复后，树行仍有两类可消除的重复工作。

**目录类型查询。** 绘制每行时调用 `Path::is_dir`，仍会访问文件系统。现在使用工作区扫描已有的数据生成 `workspace_directories`，并在[工作区树更新](../../../crates/editor-app/src/editor/documents.rs)时与节点一起整体替换。索引覆盖根目录、空目录和推导出的祖先；新快照移除旧的重命名、删除或类型变更条目。实际文件操作仍保留实时磁盘校验。

**主题定义复制。** 原先每行都调用 `active_theme`，重复进行主题查询和完整定义克隆。现在一次树渲染只取一次主题，供当次各行复用；没有跨帧冻结主题。

目录索引测试验证了无需真实磁盘路径也能正确分类、空目录不会变成文件、新快照不会残留旧分类。图标、文件树和窗口几何的针对性测试合计 14 项通过。

后续有效真实拖动的长段达到约 **114.477 次位置变化/秒**，另一个段为 **112.706 次/秒**；树 prepaint 已降至约 **1 ms/帧**的量级。期间一次过期采样只有松键和零位置变化，已排除，不能作为优化效果证据。用户后来反馈长文件、多标签时仍会变卡，因此继续排查。

## 第五步：用对照排除错误方向

这一阶段主要改善诊断，没有把每个实验都保留为产品代码。

| 对照 | 观察 | 后续决定 |
| --- | --- | --- |
| 改变活动文件和后台标签数 | 自动全量刷新约 134–144 次 draw/秒，没有简单的“标签越多越慢”关系 | 不据此否定用户对长文件的反馈；活动内容和后台负载尚未完全受控 |
| 同一诊断 EXE 关闭内部采集 | 真实位置更新约 114.451 次/秒，与开启时约 114.477 接近 | 采集开关不是该轮主要降速来源；编译进去的 profiler 开销仍未被单独排除 |
| 真实拖动中主动连续 `refresh()` 8 秒 | 实际窗口位置更新没有改善到目标 | 未将强制连续刷新加入产品 |
| 检查每帧全文处理的假设 | 未记录到怀疑的 `language.linked_input` 路径；已测 source styles 和标签准备不是当轮主要尖峰 | 没有据此改动文本真相来源或新增跨帧文档缓存 |

自动刷新压力测试只驱动内容绘制，不模拟持续窗口拖动。已有自动化拖动接口只产生起终点跳变，因此真实运动证据来自用户手动持续拖动与只读坐标采样。

## 第六步：定位周期性锁竞争，取得明显的跟手改善

进一步细分宿主阶段后，发现插件视图同步、语言服务同步、文档同步会轮流出现数毫秒尖峰。它们并非每帧都慢，长事件大约每 90–100 ms 出现一次。

随后直接测量 UI 获取锁的时间和后台持锁区间，确认后台 worker 在持有 `Published` 互斥锁时调用 Manager 派生状态准备，其中包含插件包元数据读取／验证。UI 在绘制过程中需要读取同一份发布状态，只能等待。

旧基准中后台持锁中位数约 **6.078 ms**；34 次超过 2 ms 的 UI preference 锁等待，**99.75%** 的累计等待时间与后台持锁区间重叠。相比单看函数耗时，这直接证实了共享锁阻塞。

修复后的发布顺序为：

```text
持有 Manager guard
  → 在 Published 锁外准备可用性、实例、诊断及执行状态等数据
  → 短暂取得 Published 锁
  → 按当前撤销代数协调并统一发布
  → 释放锁
```

准备到发布期间保留 Manager guard，避免快照失去一致性；快照不覆盖当前命令撤销代数，保留 UI 已发生的提前退役；实际命令接纳仍检查 live Manager 状态，发布快照不直接授权执行。该改动针对周期性发布路径，没有声称审计完全部其他共享锁用途。

修复版真实采样结果：

| 指标 | 修复前基准 | 修复后 capture |
| --- | ---: | ---: |
| 后台持锁中位数 | 6.078 ms | 0.045 ms |
| 后台持锁 p95 | 8.100 ms | 0.073 ms |
| UI preference 获取锁最大耗时 | 存在多次超过 2 ms 的等待 | 0.0038 ms |
| UI document 获取锁最大耗时 | 记录到 5.401 ms 等待 | 0.0002 ms |

新 capture 的 684 次后台持锁，以及两类 UI 获取锁都没有超过 2 ms 的事件。用户反馈 **“已完成，明显更顺畅”**。证据支持原有发布锁竞争尖峰在本次采样中消失。

全部三个真实拖动段仍分别保留，避免只挑最快一段：

| 完整拖动段 | 时长 | OS 位置变化频率 | GPUI draw 频率 | draw 耗时 p50 / p95 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 4.581 秒 | 105.000 次/秒 | 100.634 次/秒 | 5.677 / 7.065 ms |
| 2 | 6.572 秒 | 128.430 次/秒 | 127.213 次/秒 | 5.610 / 6.415 ms |
| 3 | 6.786 秒 | 149.876 次/秒 | 137.055 次/秒 | 4.782 / 5.627 ms |

三段统一裁去首尾各 250 ms 后，draw 频率分别为 104.143、130.936、143.184 次/秒。第三段已经接近目标，但不能代表所有场景。三段窗口尺寸、标签数和 GPUI 报告的 144 Hz 周期一致；每帧成本仍有差异，当前数据没有进一步解释其来源。

真实插件回归确认了首次激活、提前退役、禁用后重新启用、实例替换及受限工作区相关行为。两处测试夹具原先没有建立工作区，修正夹具后重跑通过，没有放松断言或改变产品权限规则。

本轮实现结束前的验证记录为：

- 图标、树分类和窗口保存针对性回归：14 项通过。
- 两项快照发布／冷命令首次启动真实回归：2 项通过、0 项忽略；真实 shortcuts 生命周期及受限工作区回归此前也已通过。

## 如何理解“从卡顿到流畅”

本次保留的优化逐步减少了 **UI 热路径中的同步文件工作、重复计算和共享锁等待**。前半程降低每帧树绘制的固定成本，后半程消除周期性抢不到共享锁的停顿，这与用户最后反馈明显更顺畅相符。

约 **60 → 97 → 114 次/秒**是不同阶段的代表性窗口位置采样，不是严格单变量 A/B，也不能将最后的 149.876 次位置变化/秒写成“稳定 150 FPS”。应始终区分：

- **OS 位置更新**：窗口坐标改变的次数，同一显示周期可以变化多次。
- **GPUI draw／CPU present**：应用绘制和平台提交调用的频率与耗时。
- **屏幕呈现及输入到显示延迟**：需要独立测量，本轮没有直接取得。

当前已确认的是具体瓶颈被移除、部分长等待消失，以及用户的跟手感改善。普通 Release 同场景复测、长文件规模的受控对照、异刷新率跨屏和模式切换仍待验证；240/360 Hz、VRR 与所有 DPI 组合没有物理验收。后续继续沿用当前显示器刷新节奏，不以固定高刷定时器掩盖慢帧。
